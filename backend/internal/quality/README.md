# 质量守护与资源证明

这项产品服务于多账号、多出口的 Build 服务运营者。用户要知道的是异常跟随账号还是出口，以及现在应当保留哪个资源、暂停哪个资源。完成多少任务、积累多少错误、显示多高分数，都不等于回答了这个问题。

一次事件只触发暂时保护。新案件和主动检测共享完整有效观测及 R1/R2/R3 证明规则，只有本窗口的 A 型观测能够建立正常对照。证明依赖 A/B 四态模型与窗口内状态稳定，不声称读取上游标记或给出已校准概率。案件拥有限制与恢复，主动检测只生成报告。

## “降智”的含义与四种资源组合

本模块中“降智”指请求正常模型 A 时，上游静默改走替代模型/处理路径 B。它不是同一模型偶尔答错题、回答变短或主观感觉能力下降。上游可能仍返回请求中的模型名称，HTTP 也可能成功，因此请求成功不等于获得了所请求的正常模型。A/B 是便于描述这种路由现象的类别，不是已取得上游内部模型权重或风控字段的证明。

在已验证的 Build 推理请求条件下，A 型响应出现非空可见思考，B 型响应持续缺少可见思考，并伴随可重现的输入 token 差分变化。账号状态与目标侧出口状态是两个独立变量：

| 账号状态 | 出口状态 | 预期路由表现 | 归因所需对照 |
| --- | --- | --- | --- |
| 正常 | 正常 | A 型，有可见思考 | 有效 A 同时证明两个端点正常（R1） |
| 异常 | 正常 | B 型；通过正常出口仍复现 | 目标 B，加同出口另一账号的有效 A（R2） |
| 正常 | 异常 | B 型；同账号换回正常出口恢复 A | 目标 B，加同账号另一实际出口的有效 A（R3） |
| 异常 | 异常 | B 型；单独这一格无法分辨两个因素 | 分别在正常对端上取得账号 R2 和出口 R3，不能仅凭这一格归因 |

这四格是解释与复现实验的资源模型，不是把任何一次 B 型响应直接标为账号异常。只有正常账号与正常出口配对才预期得到 A；没有合格正对照时，整池一致也不能证明整池正常。系统没有读取上游风控标记的可靠接口，界面中的资源异常表达受控实验支持的行为归因。

## 脱敏对照与复现条件

受控对照曾观察到下面的简化向量。账号只分“正常对照/疑似账号”，出口只分“正常对照/疑似出口”；不保存实际身份、地址、凭据、请求 ID 或原始响应。表中数值是特定模板下的校准观察，不是永久规则或测试夹具：

| 组合 | 可见思考 | 512 个 a 的输入 tokens | 2048 个 a 的输入 tokens | 长短差分 |
| --- | --- | ---: | ---: | ---: |
| 正常账号 × 正常出口 | 有 | 265 | 457 | 192 |
| 疑似账号 × 正常出口 | 无 | 248 | 344 | 96 |
| 正常账号 × 疑似出口 | 无 | 248 | 344 | 96 |
| 同一正常账号换回正常出口 | 有 | 265 | 457 | 192 |
| 异常账号 × 异常出口 | 无 | 248 | 未测 | 未测 |

复现时固定支持推理的同一 Build 模型、Responses、`low`、无工具、新会话，以及前缀 `Reply only OK. Data: `；后接 512/2048/512 个重复 `a`。完整读取成功终态和 EOF，确认 usage 存在、两个短样本一致，且生成前后目标侧路径没有变化。先后都要复测正常控制组合，并跨多个实际出口或独立账号重复。产品的具体门槛、预算和结果见下文“管理界面”，不能只跑表中一格就认定资源异常。

账号不变、换出口后 B→A，支持出口方向异常；同出口控制账号为 A、目标账号跨多个正常出口仍为 B，支持账号方向异常。两类异常的 token 向量一致，支持存在共同的替代处理路径。长短差分不同无法仅由固定系统前缀的常量偏移解释，与分词或随输入变化的处理机制不同相符；但上游自报 usage 不能独立证明具体模型权重身份。

长短输入用于探索处理路径差异，主动证明协议只使用一个固定短模板，不重复发送长输入。双异常组合已用短模板交叉验证：账号在正常出口为 B、正常账号在异常出口为 B、正常对照组合为 A，两条异常证明可以同时成立；缺少 A 的全 B 观测只能返回无法判定。

token 差分应结合可见思考解释，但不是主动判决的必需条件。`model` 回显、`system_fingerprint`、正的 `reasoning_tokens` 都不能代替可见思考；正常样本的 `cached_tokens` 也不恒定。时延和 SSE 文本增量大小受排队、缓冲等影响，只能作为旁证。网络错误、超时、响应不完整、usage 缺失或路径不稳定属于无法测量，不能变成 B 型票。目标侧 IPv4/IPv6 可能与普通查 IP 服务不同；同一节点 ID 也不保证每次使用相同出口。

案件共用协议的真实四格验证使用隔离案件数据库、真实上游和已核实固定出口，未向生产案件写入试验事件。一次四格执行分别消耗 1/2/3/4 次生成：

| 目标账号 / 出口 | 有效观测顺序 | 结果 |
| --- | --- | --- |
| 正常 / 正常 | A | R1，双方正常 |
| 异常 / 正常 | B、A | R2，账号异常；出口有 R1 |
| 正常 / 异常 | B、B、A | R3，出口异常；账号有 R1 |
| 异常 / 异常 | B、B、B、A | 独立 R2 与 R3，双方异常 |

这些次数记录一次实际自适应执行，不是固定请求配额或成功保证；候选、失败和窗口变化会改变路径。与全 B、冲突、缺失控制等合成测试一起验证判定及弃权分支，不代表能从黑盒无条件读取上游内部标记。复现时构造隔离本地案件、执行正式证明队列、检查最终当事方限制，再人工释放隔离案件；直连异常出口通过仅本机临时固定通道观测，不能把临时测试节点写进生产配置。

## 实时守卫与主动复核的分工

| 流程 | 触发与目的 | 证据与结果 | 状态边界 |
| --- | --- | --- | --- |
| 实时守卫 | 用户推理请求被动触发，尽快决定本次响应是否可交付 | 有效思考可立即放行；无思考先输出正文等信号可立即扣留；故障独立分类 | 沿既有事件与案件流程处理，不等待主动检查 |
| 主动资源检测 | 管理员主动选择账号/出口，用于检查资源或二次确认 | 完整流分类、同窗口 A 型正对照与账号/出口交叉证明；token 仅作旁证；输出正常、异常或无法判定 | 独立任务和报告，不给案件投票、不自动立案或解封，不改变实时守卫阈值 |

两者复用协议事实解析，但实验、判定时间和状态写入分别持有。主动任务仍消耗真实上游额度及共享账号/网络容量，通过有界队列、并发与总预算限制影响；“互不改写结论”不表示资源消耗完全隔离。主动正常结果可供人工复核，不能替另一个案件解除限制，也不能清除上游状态。

真实正反对照支持了“可见思考放行”和“无思考先出正文扣留”这两个分支，覆盖 Responses SSE、Chat SSE 与 Responses JSON。时序回放还显示：普通请求可能先触发首事件超时，而高推理/工具请求在较长预算内才出现扣留证据；必须按实际请求类别使用预算，超时本身不构成降智证据。推理项闭合与完成终态兜底尚未取得同等真实正反样本，依靠合成协议回归覆盖，不能宣称所有分支都经过真实资源验证。完整主动测量中若先有扣留信号、后出现思考，保留冲突，不能由晚到思考覆盖前面的事实。

以上是已观察行为与判别边界，不是跨模型、跨时间的准确率保证。上游变更后应重新建立正常基线；模型、协议、工具或推理档位变化时不能直接复用旧数字。实际账号/出口映射、原始轨迹及运行报告不进入 Git；本地材料位置由项目本地索引维护。仓库只维护脱敏机制说明和最小人工构造回归。

## 内部职责与依赖

`journal.AccountAllowed` 以原生 SQL 联查 registry 拥有的 `q_account_state`/`q_case_party` 表(最终准入判定);这两张表的列名与状态值是 journal/registry 的显式共同合同,变更须两侧同步。

`model` 定义案件、当事方、任务、持久事件和证据快照，并提供确定性的聚合与互证规则，不依赖数据库或业务服务。`court` 通过 `StateStore` 和 `ProbeReader` 编排立案、有限实验和结案；`investigator` 通过任务与测量端口执行；`events` 通过 journal 端口消费已持久接受的事实；`enforcement` 通过状态、节点与轮换端口执行出口处置。`management` 通过配置应用接口和只读查询接口提供管理用例。

`registry` 实现案件/身份/限制的原子存取与资格投影，`journal` 实现持久事实和可恢复 outbox，`evidence` 实现观测存储及滑窗发布。这三个包不被业务流程直接导入。组合根创建存储、注入端口并关闭资源；court 不创建任务存储，management 不持有可执行 SQL 的 Store。接口返回 `model` 中的值，不返回 GORM 或实现包 DTO。

拆分保持原有表、JSON 字段、事件身份、协调租约和条件更新。证据策略配置与 logger 分别注入；热改窗口仍先重载成功再发布。类型位置改变不代表可以改变案件协议或解除旧限制。

court 与 enforcement 的构造函数不启动任务；组合根调用非阻塞 `Run`，随后由 `Close(ctx)` 取消并等待循环退出。Close 在未启动时关闭启动入口，重复调用仍等待同一个完成信号；一次关闭超时不代表任务已退出，也不能让下一次关闭绕过等待后提前关闭数据库。court 的周期评估在首个间隔后执行，enforcement 启动后立即观察一次出口。

## 新案件的共用证明协议

新质量事件创建 `resource-proof-case-v1` 案件；测量规格为下文 `resource-proof-v2`。案件保存一个 `case_proof` 队列任务，双方作为同批目标，共用主动检测的完整流测量器、A/B/未知/冲突分类、候选规划和 R1/R2/R3 纯规则。生产事件只作为调查来源，不因实时扣留就成为完整 B 样本。无可见思考但失败、不完整、纯拒答或路径未核实，仍是未知。

两个目标共享最多 6 次测量尝试，只有账号目标时最多 5 次；每次最多一次物理生成，前置失败可能不生成。初始候选至多 8 个辅助账号、4 个固定出口，候选资格不代表正常。证明充分即停止，不要求多账号/多出口重复票数；全 B 无正常锚点、窗口冲突或预算耗尽均保留无法判定。双异常的最小证书为共享一个正常锚点的 3 条有效观测，实际寻找证书可能多于 3 次。目标原组合也测量时，典型双异常路径用 4 次。

案件在查询候选之前原子立案并保留原截止时间；候选查询失败时保留案件，后续在原期限内恢复准备。准备完成后的计划与预算固定，重复派发返回同一任务；终态或失联任务不重新执行。每次生成前持久预留预算，进度受 owner、租约和 revision CAS 保护，结案取消后迟到结果无权写入。手动批次与案件证明合计最多 2 个运行任务，共用既有物理容量；案件不占手动资源队列名额。案件证据不投影成流量票，也不进入主动检测历史。

证据窗口固定 180 秒，每次完整测量上限 45 秒；任务还受本案原绝对截止时间限制（默认 10 分钟）。案件评估重新运行同一纯证明器；已经过期的证书仍可查阅，但不能形成新的自动限制。不跨窗借用正常锚点，身份/路径漂移与冲突不按多数票解决。施加限制或提前释放前，对证书引用的观测重新读取当前身份组、凭据代际、节点 binding 和 epoch；变化只使涉及该观测的证书失效，独立证书仍可成立。事实源读取失败在原期限内延后，期限耗尽时不以缺失事实施加限制。轮换池、无法固定或未登记的出口不能冒充稳定出口；本机直连没有可核实管理节点时，只检测可独立证明的账号方向。

账号与出口分别输出正常、异常、无法判定。两方异常对应 `both_guilty`；一方异常、另一方未知，只限制已证明异常的一方，报告明确保留另一方未知。无法判定不等于正常，本案期限结束后释放未被证明异常一方的临时限制。运行中的有效 R1 可提前解除本案对应方冻结，不影响其他案件；失败或取消的任务仅保留测量历史，不能以中途证书新作异常裁决或提前释放。出口换代后，不把旧证据施加到新出口，已独立成立且仍有效的账号证明可以保留。人工复核、其他案件持有的限制、账号启停/认证/配额和网络处置继续由既有 owner 管理。

新协议不从传输失败推断模型 B，也不通过重复错误构造降智裁决；认证、配额、冷却和网络可用性仍由各自运行时管理。系统不再执行旧的差分、陪审、投票门槛与可用性裁决。

管理端以用户语言展示调查结论、双方处置、按时间排列的对照检测及因果说明，账号和出口以名称为主。判定依据可定位到对应检测；不向用户展示规则编号、内部协议版本或地址摘要。协议标识和原始证书仍保留在 API 与持久记录供开发审计。案件的资源判决与当事方处置分开展示；历史观测证书不能解读为当前资源永久正常或异常。

### 升级和回退

SQLite/PostgreSQL 扩展 `q_probe_task.direction` 的 `resource_check`、`case_proof` 值，以及 `q_case.status/verdict` 的 `both_guilty` 值，保留历史任务、owner、报告、案件与索引。SQLite 重建约束复制已有列，PostgreSQL 在现有 advisory lock 事务内更新约束。原 `check_report_json`、`check_revision` 与任务租约复用，不另建案件测量账本。先排空旧 worker，再升级；旧程序不认识新任务及双异常限制持有关系，不能混跑。回退只能到理解这些合同的版本，或在没有新任务/裁决写入前使用升级前一致性备份；不能让旧程序忽略双异常限制，也不能清理新业务数据来迎合旧约束。

当前唯一执行协议是 `resource-proof-v2`，案件以 `resource-proof-case-v1` 封装。旧测量协议和阈值裁决已删除。旧未结案件评估时以“协议已停用、证据不足”结束并解除本案临时限制；旧待执行测量被拒绝，不发出上游请求。已结案件、原始报告及已接受的持久事实保留，不重新解释为新证明，也不自动撤销已存在的终局限制；人工复核仍可解除本案限制。

## 案件独立释放

有效 A 观测可直接证明对应账号与实际出口在本窗口正常。证书经当前身份、凭据、binding 和 epoch 核实后，可以先解除对应一方的本案冻结。等待、失败、缺少路径验证或正常/异常冲突不能作为正常证据。

这项排除只影响本案的临时限制，不能提前定罪。另一方继续当前有界证明搜索，并保留原截止时间。释放在下一次后台评估时执行，默认评估间隔 15 秒；不承诺在最后一个测试完成的同一瞬间执行。

`registry/clearance.go` 在一个事务中更新当事方处置和释放证据，再发布资格快照。`early_releases` 保存时间、原因和协议版本。其他案件的冻结或判决仍然有效。计划器不会重新冻结已经释放的当事方，同一事件也不会因提前释放再开一个案件。事务失败回滚、重放、重启、其他案件持有限制、另一组仍等待和最终结案均有回归覆盖。

释放不只在调度轴上生效：本次动作确实把账号从羁押变为可用时，组合根注入的通知让账号轴立即清掉它携带的质量标记与随之而来的瞬态冷却（`quality_idle_timeout`、`missing_thinking`），被证明无罪的账号不必再等这段冷却自然到期。仍被另一个案件羁押的账号不被通知，因此一个案件不能替另一个案件解禁；当前限制若是纯传输事实（如上游 429），也不在解除范围内——那属于账号轴，出口裁决不得抹掉它。通知失败只记日志，不改写已提交的裁决，也不回滚释放。

## 持久化、恢复与处置

`model/resource_proof.go` 拥有纯证明规则，`court/proof.go` 将共享证书映射为案件处置，`court/workflow.go` 编排恢复和评估，`investigator/resource_planner.go` 选择补齐证明所需的未测试组合。`registry/experiment.go` 提供两个事务：

1. 建立案件、登记双方、写双方调度冻结，然后一次发布内存资格快照。
2. 结案、保存解释、更新双方处置与调度状态、取消未完成任务，然后一次发布快照。

结案条件更新只接受 investigating，重放不会改写既有结论。结案后迟到的探测写回被拒绝。证明进度独立持久化，不写入流量聚合窗口。单个案件评估出错会被报告，其他案件继续评估。

8 个工作槽独立认领 pending；running 保存进程 owner 与 3 分钟租约，每 30 秒续租，结果写回检查未过期 owner。重启仅回收过期或旧版无 owner 的工作；活跃副本不被取消，工作中断不被计算为账号异常。当前证明终态与已保存的报告 revision 一致；已接受的历史 outbox 仍按稳定事件 ID 恢复，不产生新的历史测量。截止时间从案件创建时计算，重启和设置变化都不能重置它。数据库不可写时不能承诺成功结案，系统保留保护、报告失败；数据库恢复后的评估继续收口。

IP epoch 改变后旧出口方退出，不把旧结论施加到新 IP。单方或双方异常判决中的固定与 webhook 出口按当前 epoch 禁用；池出口沿用当前 epoch 保护，变化后释放。出口身份是双地址族的：任一非空族变化即翻 epoch（与 egress 轮换验证同一把尺子，WARP/MicroWARP 类隧道重启后 IPv4 稳定而 IPv6 轮换是常态）；旧档案缺失的一族首次观测到时只采纳补写基线（`current_ipv6` 列，AutoMigrate 加列，旧行默认空串），不翻 epoch——升级本身不得释放仍有效的限制。轮换成功记账后由组合根立即驱动执行所的单节点观测（`ObserveNodeExit`），解禁不再等下一个检测节拍；周期轮询仍是兜底。账号归因只限制案件账号，不把其他健康对照账号连带限制。

人工可以填写复核原因并解除本案限制。节点人工解禁则在一个事务中解除该节点当前 epoch 的全部案件限制，保留各案件原始裁决与解除原因，不释放账号；已解除的出口方不会被同案后续裁决重新限制，新事件仍可正常开案。原始结论和证据完整嵌入复核记录；其他仍有效的案件继续持有自己的限制。首次升级不清空案件、证据或状态。普通已释放案件与完整测试统一保留 30 天；限制类判决保留到人工解除后再进入保留周期。独立孤儿终态测试保留 14 天。

多实例部署使用 PostgreSQL 与 Redis。主请求和探针共享账号并发与响应缓冲预算；探针额外共享最多 2 个测量槽、每个账号或身份组 1 个槽。测量最长 90 秒，全部探针容量租约为 2 分钟，失联后无需等待生产长请求 TTL；短探针租约不会缩短同键生产租约。

轮换执行入口使用共享节点租约和 Redis 滚动一小时额度。每次尝试在调用 webhook 前持久化次数与开始时间；失败、超时及进程退出都保留该次消耗。自动巡检不重置次数，只有人工触发可在取得同一节点租约后重开周期。单次执行最多 4 分钟，所有权租约为 4 分 30 秒；依赖不可用或尝试预留写入失败时不发出 webhook。轮换 worker 支持禁用后热启用，执行所关闭会取消正在读取的节点与巡检工作。

court 使用有 owner 的跨实例协调租约，事务内再次验证所有者。过期案件先于流量聚合、新开案与维护工作处理，每案最多 1 秒；未到期案件最多 5 秒，供较大候选池查询与补测计划使用。两者都只占总轮次剩余预算的一部分；处理游标持久化，慢案件不会反复占据队首。案件准备阶段一次读取候选账号和节点，冻结计划；执行时仍核实当前资格与身份。仍有大量积压时需要多个轮次，数据库整体不可写时无法保证释放成功。

当前代际单独存储于 `q_node_epoch`，与追加档案事务更新。状态快照按 revision 重载，未变化时跳过；探针入队只锁定并读取关联案件，不重建全局状态。最终账号/出口准入直接查库。PostgreSQL 首次建表及升级在 advisory lock 保护的事务中串行，支持并发启动。代际指针和完成标记在同一事务初始化，失败可重试；升级前应排空旧工作进程，不能混跑仍只写历史代际的旧版本。

出口探测在发起网络测量前，由数据库递增节点的 `probe_sequence`；结果携带该版本写回，只有最新已发起且尚未提交的版本可以写入 `probe_revision`。执行所消费这个版本，登记处将 `observation_revision` 与 IP 代际、旧限制释放和旧当事方撤下放在同一事务。重复或迟到版本无权推进代际；同 IP 的新观测也推进版本水位。顺序不依赖各实例本地时钟。观测身份按地址族比较：探活的 `ipv4_exit_ip`/`ipv6_exit_ip` 分别构成身份两侧，聚合 `exit_ip`（IPv4 优先）仅用于展示与台账。升级前保存的无版本 IP 仅作历史信息，需新探测后才可作为自动解除依据；旧工作进程必须排空，因为旧写入方不会遵守版本校验。

案件去重使用 `q_incident_closure` 保存每个 `(account_id, node_id, epoch)` 的最新结案时间，随结案事务更新。首次升级从历史回填，回填与初始化标记一起提交；失败可重试，后续启动不重复扫描历史。单事件按键查询，周期发现仅批量读取待处理事件；该投影不进入全局状态快照，并保留到显式质量状态重置，以防迟到事件在原始案件清理后重新立案。出口与账号持有方查询有对应复合索引，健康准入不再扫描全部案件历史。

主请求完成事实与恢复、门控/交付和资源预算的详细契约见 [实时响应守卫](guard/README.md)。

## 管理界面

账号页的“可用性检测”检查凭据、额度和普通响应；账号和代理节点页的“风控检测”测量指定资源在 Build 推理面上的完整响应，并通过正常对照归因，不需要先产生案件。行菜单和批量工具栏共用 `entities/guard/ResourceCheckDialog`，每批最多 32 个资源。`POST /api/admin/v1/quality/resource-checks` 接收 `{"kind":"account|node","resource_ids":["1","2"],"model":"公开模型 ID"}`，资源与任务 ID、身份及版本以十进制字符串传输，POST 也兼容整数 ID 输入；202 逐项返回任务 ID 或失败码；部分接受明确保留，重试复用该资源已有的在途任务。GET 使用 `kind` 和逗号分隔 `resource_ids`，每资源返回最近 5 次报告及在途进度。`management.ResourceChecks` 拥有候选准备与提交，`investigator` 拥有有界实验执行，`model` 拥有归因规则，gateway 拥有生成和资源取得，egress 拥有目标路径核实。检查不改写案件、启停或质量限制。

主动检测详情按选择范围组织：单个资源直接显示结论与检测经过；多个资源显示按各目标最近一次报告汇总的概览、可搜索资源列表和选中资源详情，不把不同时刻的最近报告当作同一批次。每个资源可切换最近 5 次历史记录，轮询不覆盖正在查看的历史。报告中的检测尝试和生成请求为该报告所属批次的共享计数，不按目标重复累计；默认只显示目标直接参与或其证书引用的检测，可展开整批记录。证据链接严格匹配已保存证书的观测 ID 和窗口，不在前端重算归因。任务仍在运行、失败或取消时，不将中途证书呈现为最终结论；过期的正常证据显示“检测时正常”并提示复测。界面使用资源名称、思考状态和对照解释，不展示内部规则编号、协议名称或地址摘要；名称缺失保留十进制字符串 ID。查询随弹窗卸载取消，已接受的服务端任务仍继续。

`resource-proof-v2` 使用固定前缀 `Reply only OK. Data: ` 加 512 个重复 `a`，同一 Build 推理模型、Responses、无工具、`low`、256 token 输出上限，每次新会话且最多一次物理生成。完整读取成功终态与 EOF、取得 usage、核实实际账号/凭据代际、策略规格和生成前后目标同域出口后，才分类：有有效可见思考为 A；无思考且确有普通文本输出为 B。空响应、纯拒答、工具等规格外输出、失败、不完整、路径无法核实均为未知；先正文后思考为冲突。输入/cached/reasoning token 只保留辅助事实，不要求差分、不充当正常锚点，也不自动追加长输入。

归因假设是 `B(a,e) = account_bad(a) OR exit_bad(e)`，且同一证明窗口内状态稳定。纯规则 `model/resource_proof.go` 对本窗口全部可采观测先检查一致性，再应用：

- R1：`A(C,P)` 证明 C 与 P 在本次作用域内正常。
- R2：`B(X,P) + A(C,P)` 证明 X 账号方向异常。
- R3：`B(C,P) + A(C,N)` 证明 P 出口方向异常。

单条 B 只能说明组合异常；全部 B 而没有 A 不能归因。目标得到 A 即停止；异常目标与 A 型对照闭合证明即停止，不补齐无关矩阵。正常证书最少 1 条，单资源异常最少 2 条；指定账号与出口双异常在共享正常锚点时最少 3 条。找到证书可能需要额外查找请求，未知资源池不存在对所有真实状态都最省的固定顺序。账号身份组与实际出口地址摘要/地址族用来合并别名，节点 ID 不代表不同 IP。整个窗口有矛盾时返回无法判定，不丢弃反证或多数投票。结论支持 A/B 行为归因，不声称读取上游标记或证明具体模型权重。

`investigator/resource_planner.go` 优先测量目标或能解除已知 B 歧义的控制组合，有正常相反端时优先复用；候选随机打散并保存选择种子。连续 B 后跨另一轴寻找对照，不在同一轴无限追加。已知异常端点不继续与未知目标配对；已试组合不自动重放，确定的账号资格/请求拒绝及不支持规格不会作为 B。目标无法继续测量时停止无助于证明的控制调用。

每批至多 32 个目标，共享至多 8 个辅助账号、4 个辅助固定节点和 `目标数 + 4` 次测量尝试预算（单目标最多 5 次，批次最多 36 次）。未生成的路径前置失败也消耗尝试预算；实际生成尝试与 trace 次数另记。目标和候选都不以历史“正常”标签作为证据。只有一个可测组合时仍可先测，A 足以结束；没有对照不是拒绝首次测量的理由。当前目标接口使用固定节点，不以普通外部查 IP 或另一代理代替本机直连。新节点尚未登记出口代际时，在生成前返回 `path_unregistered`，本窗口不再对该节点发送控制请求；其他独立目标继续。先完成连通性检查，由现有出口观测循环登记后重新检测，不以默认 epoch 0 冒充已登记。

每次测量最多 45 秒、完整流最多 1 MiB。批次最长 12 分钟，证据窗口从开始固定 180 秒，不滑动延长。同一窗口内凭据、身份组、binding、epoch 或实际路径变化使归因失效；不完整响应中独立核实的身份和路径变化也参与冲突检查，登记状态丢失不能冒充原 epoch 不变。过期后未完成目标建立新窗口，已闭合窗口保留历史证书，旧锚点不跨窗复用。相同身份的多个目标共享一条证据，不重复调用；辅助候选按执行时可核实的身份去重。正常报告过期标明需复测。小输出上限不是隐藏推理费用的保证。

主动资源检测共有 32 个在途资源名额。一个 `q_probe_task` 行拥有整个批次的规格、预算、观测、证书及 revision，`q_resource_check_target` 只索引目标到批次；不同目标引用同一物理观测 ID，不复制成多票。全局最多两个资源批次 running，批次内部串行决策；同一账号身份仍经过共享测量槽。每次调用前持久预留预算，进度通过有效 owner、租约、单调 revision CAS 更新；存储复核预算与冻结计划一致。保存失败立即停止新调用，内存 revision 只在进度写入成功后推进；任务终结仍校验最后确认的 revision 和有效所有者。排队超过 4 小时取消；失联运行批次保留已保存进度并取消，不能从头重跑。关闭浏览器只停止查询。重复提交复用相同规格的在途引用，不同规格明确返回冲突。部分接受保持可查询。主动任务不能改写案件限制；新案件另行持有证明任务，共享本节测量与归因规则。已停用的协议不再参与执行或判决。

主动检查绕过既有质量羁押资格以便复核，仍遵守账号启停、认证、冷却、配额和并发限制；这些条件阻止测量时显示无法判定。检查不立案、不写裁决证据投影、不自动解除任何案件。人工复核仍经既有带原因的案件解除操作，原裁决和其他案件限制保留。资源检测采用上述 4 小时排队期限；运行任务沿用 owner、租约、续租与取消收口，终态报告随独立孤儿任务保留 14 天。

持久化为 `q_probe_task` 增加 `check_report_json`、`check_revision` 与 `manual_slots`，任务方向包括主动检测 `resource_check` 和案件证明 `case_proof`。资源计划随 `experiment_json` 保存，`q_resource_check_target` 索引目标到任务。SQLite 在事务中重建约束、复制已有字段并恢复索引；PostgreSQL 在升级事务和 advisory lock 内扩展约束。从已发布案件版本升级保留原任务、租约、案件和证据。原有案件记录不会转成主动报告或新证书。工作进程及回退要求见“升级和回退”。

质量防护默认进入归因案件。案件详情展示：实际账号和出口名称/邮箱/IP 档案、当前处置、固定的截止时间、按时间排列的检测、每个资源的证明依据、无法判定原因和结束原因、人工复核操作。案件详情跟随当前查询结果更新，完整测试按 case_id 加载，不受全局最近测试窗口截断。

测试记录页只展示当前案件证明任务；查询在最近 50 条限制之前筛选 `case_proof`，按发起时间、ID 倒序排列。旧单次测量不再进入此页，不提供旧检测方式筛选或旧报告分支。页面以搜索和结果下拉筛选组织记录；卡片展示检测摘要，表格将账号、出口、结果和时间分列。统计以任务为单位，不重复累计同一任务的多个目标；运行、失败和取消优先于中途证书，结论取各目标证明结果，不读取通用 `result` 字段猜测正常或异常。报告随轮询更新，可切换账号／出口查看证明与检测经过；当前裁决及限制通过所属案件查看。身份查询只取记录实际引用的账号，证明中的字符串 ID 保持精度。

旧报告保留在持久数据中；前端不再实现旧进度槽、票数、置信度和旧测量详情组件。缺少当前证明的案件不展示新协议结论。账号名称按案件和探针实际引用的 ID 批量读取，每批最多 500 个；不扫描整个账号池或加载凭据、额度和审计。受限账号数量使用账号管理查询的分页前质量筛选，只统计仍存在的账号。名称与受限数量共享账号缓存失效范围，删除、人工复核后刷新，重新进入页面强制读取并每 10 秒轮询。没有可用名称的已删除资源仍显示保留 ID；历史记录不补造名称，名称不可用时明确提示。

质量设置的“检测与记录”只提供案件调查期限、观测保留期、证据统计滑窗。判定规则和每批有界预算属于证明协议，不提供旧的差分次数、陪审数量、投票门槛或旧探针预算。出口轮换总容量归网络设置管理。设置更新继续使用 revision CAS、持久意图与本实例应用状态；先应用可能失败的证据窗口，再应用调查期限，失败后按已保存版本重试。

## 验证与后续迭代

新增规则回归覆盖账号降智、重复响应失败、出口异常、两边正常、两边降智、单次异常、共享 IP、未核实路径、匹配控制失败、凭据不可用、正常反证、缺少出口校准、陪审不足、重复账号、等待与取消、别名路径反证。

事务故障注入验证开案/结案回滚、双方资格一致、重放与迟到结果；生命周期验证设置变化不延长期限、一个失败案件不阻塞另一案件结束、共享资源释放与 IP epoch 退出。修改规则时先用人工构造的最小案件样本固定要改变的行为，再修改纯判断函数；协议版本与案件规则保留，历史不能静默改判。

下一步运行数据应围绕人工复核结论、被推翻的假设、匹配控制不可用比例、独立路径不足和实际结案时延迭代。只有经过真实样本验证和校准，才考虑引入概率模型；不应再通过任意增加权重来修复单个案件。

## 本地验证

在 `backend/` 运行 `go test ./...`，并对质量包、应用接线和管理接口执行 `go test -race`。在 `frontend/` 运行 `pnpm test`、`pnpm exec tsc -b` 和 `pnpm lint`。

部署实例、真实案件、请求样本与本地环境记录不随源码提交。测试语料使用构造数据或最小化后的解析失败输入。

实验规格随案件与任务持久化。新案件使用本页“新案件的共用证明协议”，主动检测使用同一测量与证明标准。不支持的旧协议不执行、不产生新判决；已结案件不自动重开。实验不可支持与调查对象缺失有独立结案原因，不记作证据已齐。

案件报告的更新必须保持冻结实验中的整数精度，尤其随机种子、账号/出口 ID 和版本号。读写通用 JSON envelope 时使用 `json.Number`，不能经过 float64 后重新保存；否则提前释放后的下一次评估会误认为实验不匹配。
